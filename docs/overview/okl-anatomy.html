Anatomy of okl · Keeps your coding agent true to your rules, specs and docs. Keeps them true to the code. Keeps learning as you build.

Load your rules.
Hold your agent to them.
Keep learning as you build.

Start okl with the rules, ADRs, standards and specs you already have, loaded as lessons that cite their source. It briefs your coding agent with the ones that share each task's words, on every prompt in Claude Code and on request in other MCP agents, and when the code a lesson covers changes, the pre-push hook, where it is installed, holds the push until its check passes again, or the code is back to what passed. New rules, mistakes, drift and failing tests keep adding lessons as you build.

6

Re-checked or retired

You decide

okl reverify lists each stale lesson's stored check and re-runs it once you confirm. A pass stamps the lesson again; a fail means fix the code, or change the lesson on purpose.

Claude Code When the agent first stops after changing files, it asks what the work taught, listing up to five lessons it was briefed on and five whose files changed. okl update keeps the proof unless the files change; okl retire keeps the reason.

5

Held when code moves

okl runs it

Commit a change to a file a lesson covers and its proof is stale. The push waits, and any briefing that includes the lesson marks it STALE, until its check passes again or the code is back to what passed.

It compares content with the proven commit, so putting the code back clears it. okl init installs the hook in that clone, and --no-verify skips it; okl init --ci gates every PR in CI instead, and --git-hook keeps both.

4

Briefed before each task

okl runs it, in Claude Code

okl shows up to five lessons that share enough of the task's subject, lists the rest that matched in a line each, and puts them in the agent's context first. A lesson no check backs is marked UNCHECKED: advice, not proof.

Claude Code A hook runs on every prompt; if okl can't brief, the prompt is blocked or told so. Other MCP agents can call okl_check; nothing calls it for them.

2

Written as a lesson

You decide

You or your agent write it down in one shape: when you see this, do that, because. It can name the files it covers.

Scope repo briefs only here; scope org can reach other repos once it is in a pack, a JSON file in git they load with okl seed. The store is one gitignored file in each clone; no server needed.

3

Proven by your check

okl runs it

okl runs the check you chose and stamps the lesson only when it passes, keeping the command, the commit and the time.

A pass is exit 0, plus the text you expect if you name one. For a lesson that covers files, a stamp with no observed run counts as unproven. Every run is logged, pass or fail.

Under the hood

How it ranks, what it costs

Rank
the prompt's subject words, up to 40 → BM25 in SQLite full-text search (title 8, body, symptom, aliases and triggers 4, fix 2, tags 1) → 36 fetched → filtered by scope, and org lessons by applies_to and the repo's interests → shown in full if three subject words, or two rare ones, are in its title, symptom, aliases or triggers, at most 5 → the rest that matched named in a line each, up to 12
Cost
about 1,580 tokens for a full briefing, a median of about 720 on real prompts, and about 0.1 s for okl check; no model runs by default, and of the three optional local models the warm one (okl warm index) adds what a lesson means at a median of 114 ms a prompt and about 1.6 GB of memory
Stale
the committed content of the lesson's files differs from the proven commit (commit times, if that commit is missing); a lesson with files and no observed pass holds the push too

Where it breaks

  • A task that shares no exact word with a lesson misses it: no stemming, so "orders" won't match "order".
  • A lesson named in a line is not shown: whether an agent opens it is not yet measured.
  • A file is watched whole: any edit needs a re-run.
  • A check proves what it tests, and nothing more.
  • Drift prompts a re-check; it is not yet a measured detector of breaks (REPORT §4af, §4ah).
