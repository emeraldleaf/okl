# How lessons should be captured and written: the research against okl

> Appendix A to [Research on each layer of okl](okl-layers-2026-11-10.md). Written on 2026-11-10 by a research agent that read each paper's own text; okl's maintainer asked the questions and checked the figures listed under *Checked at the source* in the main page against each paper's own page. Other figures here were not re-checked.

Read 2026-11-10: 35 papers, each PDF read as text; the sections read are listed with each citation. The seven papers in `docs/RELATED-WORK.md` are named only where they settle a disagreement. No product is recommended; papers by vendors are cited for their mechanism only.

## 1. okl's mechanics against the research

| Mechanic | Verdict | Why |
|---|---|---|
| **Lesson shape**: symptom, fix, triggers | Supported | Guidelines written as "when [context], do [action]" and selected for the current context beat an unconditioned list of insights (ALFWorld 79.1% vs 59.0%; WebArena 47.1% vs 21.8%) [6]. SkillsBench's audit of the skills that hurt found one common cause: "a single 'correct' pipeline without applicability boundaries" [2]. okl has the condition (the symptom) but no field for where a lesson stops applying. |
| **Abstraction level** | Supported, with a floor | Abstract sub-routines beat concrete examples [7], as in Memory Transfer Learning. Abstraction stops paying once it drops the detail an agent cannot infer: comprehensive skills gained +0.7 pp against +19.0/+21.5 for compact or standard ones [2], and repository overviews did not help [3]. okl's broad process lessons sit below that floor. |
| **Examples** | Supported, with a risk | Agents copy what they retrieve, so a wrong example spreads its error as readily as a right one spreads its fix [1]. Concrete examples bias an agent's choices [7]. Insights and examples together beat either one alone [8]. An example needs the same proof as a check. |
| **Proof**: a stored check, stamped when seen to pass | Strongly supported | Models do not correct themselves without external feedback [11], and self-correction works where reliable external feedback exists [12]. Deterministic runtime rules stopped over 90% of unsafe code executions [27]. IFEval chose checkable instructions because model judges are biased [26], and judges favour their own output [25]. |
| **Verification after admission** | Departs | Admitting only what ground truth confirmed did best on all four agents. Admitting everything fell below the unchanged starting memory on all four (e.g. 55.5 vs 67.5) [1]. okl admits first: 284 of 379 lessons have no check. |
| **Agent capture with no approval** | Departs | Skills an agent wrote for itself scored 8.1–11.5 pp *below no skills* on three agent/model pairs, while curated skills added 18.2–24.8 pp. Part of the gap was confidently wrong content, such as a hard-coded 1000× unit conversion [2]. Generated context files did worse than developer-written ones (p = 0.038) [3]. Weak models fill memory with "flawed or incomplete strategies" [9]. **Disagreement:** ReasoningBank and ACE gain from memory the agent judged itself, and a fine-tuned judge came close to ground truth in [1]. What decides the outcome is the quality of the admission signal, not who writes the lesson. **Caveat:** [2] and [3] tested content written before the task, not lessons drawn from failures. |
| **`/record` (a Claude Code command) with user confirmation** | Partly supported | The "human" judge in [1] was ground truth. No paper found measures a person approving a lesson with no evidence; a confirmation is worth what the person checks. |
| **Curated seed packs** | Supported | Curated skills added 16.6 pp [2], and developer-written context files beat generated ones [3]. **Caveat:** in [3] neither kind beat having no file significantly (+2.4%, p = 0.21), and both raised cost by about 20%. Software engineering gained least of any domain (+11.6 pp) [2]. |
| **Import of docs and ADRs** | Mixed; no direct evidence | A context file that repeats the existing docs adds nothing; the authors conclude files are useful for "non-standard coding practices" [3]. Developer-written files rarely state security (14.8%) or performance (14.5%) rules [5]. No controlled study of ADRs was found. Practitioners say specs make agents more reliable, but the specs decay and are checked against the code mainly at completion [33]. Across 88,052 PRs, specification artifacts did not reduce defects [34]. |
| **Briefing limit** (12 records) | Direction supported | Following every rule at once gets harder as rules are added, even going from one to six: a line-length rule was met 97–99% of the time alone and 2–20% of the time among six [18]. Frontier models reach 68% at 500 instructions and favour the earlier ones [17]. One to three skills beat four or more (+18–19 vs +10.1 pp) [2]. Input length alone cut performance by 13.9–85% [19]. **Disagreement:** ACE's brevity bias. Both hold if a briefing has few lessons, each with its specifics. |
| **Consolidation and retirement** | Partly supported | A curated memory beat appending the full history [9]. Each write can be an explicit add, update, delete or no-op [15]. Memory agents fail to let newer facts replace older ones (at most 28% on multi-hop questions) [16], so explicit supersede and retire beat leaving conflicts to the agent. Deleting by usage history helps when that history is reliable [1]. ACE warns against wholesale rewrites. |
| **Poisoning** | Not addressed | Poisoning under 0.1% of a store gave at least 80% attack success [13]. Queries alone got malicious records into memory 98.2% of the time [14]. okl's openings are org packs, and agent lessons drawn from issue or PR text. |
| **Measured**: models agree about half the time | Predicted | Vague criteria scored holistically produce disagreement between judges. Breaking them into yes/no questions raised agreement by 0.45 [21], and checklists raised agreement among human raters [22]. Reliability varies with what is judged [23], and percent agreement hides divergent scores [24]. |
| **Measured**: 20 lessons hold two-thirds of breaks | Consistent | Keeping examples by measured usefulness [10] and deleting by usage history [1] both weight a store by use. |

## 2. Changes, ranked by benefit against cost

1. **Hold agent-written lessons as "proposed" until they are verified.** Keep them out of the briefing, or mark them, until the check is seen red then green or a person confirms against evidence. *Benefit:* the highest; the capture studies agree on it [1][2][3][9]. *Cost:* low to moderate: a new state and a briefing filter. The #253 arm measures it.
2. **Rewrite the broad lessons judges disagree on as two to four yes/no conditions**, each naming a file, a pattern or a command ("does the diff change X without changing Y?"). *Benefit:* high. It has the largest measured gain in agreement [21][22] and moves the lesson toward a check [26]. *Cost:* low if you start with the 20 most-broken.
3. **Write checks for the 20 most-broken lessons first.** They hold two-thirds of breaks [1][10]. *Cost:* low.
4. **Add a "does not apply when" line, and lead with the action to take.** Missing boundaries were the common cause of the skills that hurt [2], and the condition is what AutoGuide added [6]. Positive phrasing has weaker support. GPT-3-era models were insensitive to negation [28]. Naming a forbidden word primes it [29] (one author, not peer-reviewed). Models fail at "don't mention X" [30]. *Cost:* low.
5. **Order the briefing by break history, and test a cap smaller than 12.** Models favour earlier instructions [17] and miss information in the middle of a long context [20], and fewer items do better [2][18]. *Cost:* one A/B arm.
6. **Import only what an agent cannot infer.** Take non-standard conventions and decisions a check can govern, not overviews [3]. Where an ADR's decision can be checked, make it a Gate, because specs nobody checks decay [33]. *Cost:* low.
7. **Treat packs, and lessons drawn from untrusted text, as untrusted until checked**, and record where each came from [13][14]. *Cost:* moderate.
8. **Ask for the intent an agent cannot infer, and store it as a check.** Asking clarifying questions improved results by up to 74% on underspecified SWE-bench tasks [31]. Intent written as tests raised pass@1 by about 46 points within five interactions with a simulated user [32]. *Cost:* moderate; okl has no capture path of this kind yet.

## 3. What the research leaves open

- **Admission.** No study compares lessons verified at admission with lessons the agent judged itself, in a real repository. The #253 arm is still the instrument.
- **The "why".** No paper found tests whether giving a reason changes rule compliance. Keep the why for people and for judges; there is no evidence it helps the agent comply.
- **Positive versus negative phrasing.** For current coding agents the evidence is only older models, non-coding tasks, or a paper that has not been reviewed.
- **ADRs and specs as agent context.** No controlled study of task outcomes exists. The one peer-reviewed test is a null result, and it measured spec artifacts (mostly ticket links) in open-source PRs, not agents given specs [34].
- **Human intent against agent lessons, head to head.** [2] and [3] compare human content with model content written before the task. None tests lessons drawn from an agent's own verified failures, or human intent and agent lessons combined.
- **Yes/no conditions for code.** Their effect on agreement was measured on judging text [21][22], not on whether a diff breaks a rule.
- **Cost.** Context files raised cost about 20% in [3] but cut median runtime 28.6% in [4] (10 repositories, efficiency only). This is unresolved.
